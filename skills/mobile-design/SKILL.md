# Mobile design

Rules distilled from a real redesign: the iOS video colour app Tona went from a pink-gradient template
to "Tona Mono", a strict black-and-white system, in one pass. The difference was not taste. It was a
short list of decisions made before any screen was drawn, and a list of things the model does by
default that had to be banned.

Work in this order. Do not skip to screens.

## 1. Find what the screen is for (2 minutes, no drawing)

Answer in one line each, from the codebase or the user's words. Ask only if nothing tells you.

- **The content.** What does the user come for: their photos, their money, their messages, a map, a
  workout? That content is the hero of every screen. The interface steps back so the content can be loud.
- **The one action** per screen. Exactly one primary button per screen.
- **The platform and code target.** SwiftUI, React Native, Flutter, Compose, or an HTML mockup if there is no app yet.

If the app already exists, read its screens and theme files first. A redesign keeps every feature and
flow and changes only how they look, unless the user asks for more.

## 2. Pick one character and write the tokens first

Name the look in two words ("Tona Mono", "Paper Ledger", "Night Field") and commit to it. Then write the
tokens file before any screen. Every screen uses only these tokens: no raw hex, no one-off sizes.

**Default character, when the user gives no brand: Mono.** It is the safest way to look expensive.

| Token | Mono value | Rule |
|---|---|---|
| background | `#000000` | screens, media stage |
| surface | `#141414` | sheets, menus |
| raised | `#1F1F1F` | pressed rows, fields |
| line | `#2B2B2B` | 1 pt separators, chip borders |
| track | `#3D3D3D` | slider tracks, secondary borders |
| text | `#FFFFFF` | primary text, 21:1 |
| textSecondary | `#A3A3A3` | secondary text, 8.4:1 |
| textTertiary | `#808080` | tertiary, 5.3:1, never on media |
| disabled | `#4D4D4D` | disabled icons, never text |
| accent | `#FFFFFF` | the only accent; on it, black |
| destructive | `#FF453A` | delete actions only |
| scrim | black 60% | behind controls on top of media |

With a brand colour: the system stays the same and the brand colour becomes the single accent.
It is used for the primary button, the selection and one or two key numbers, nothing else. A light
theme is allowed, but ship one theme done well rather than two done halfway.

**Type.** The platform font (SF Pro, Roboto, Inter for web) on the platform's dynamic text styles.
One expressive variant only for screen titles and primary buttons: expanded width (SwiftUI
`.width(.expanded)`), or a heavy weight if the platform has no width axis. Changing numbers (time,
prices, slider values) use tabular digits. Nothing below 11 pt. Titles left-aligned, large (34 pt).

**Spacing.** 4 pt grid: 2, 4, 8, 12, 16, 20, 24, 32, 48. Screen side margin 20. Inside a group 8 to 12,
between groups 24 to 32. Tap targets at least 44 × 44.

**Radii.** Three values: 0 for media (photos, video, grids), 2 for controls (buttons, chips, tiles,
fields, badges), 6 for sheets. No pills, no 16 to 24 pt "friendly" cards.

Token templates for each code target: `references/tokens.md`.

## 3. Ban the default AI look

These are what a model produces when asked for "a beautiful app". Each one alone looks fine. Together
they are why the result looks generated. Do not use any of them unless the user explicitly asks.

- Purple, pink or blue-to-purple gradients, on backgrounds, buttons or text.
- Glassmorphism: blurred translucent cards over gradients.
- Pill-shaped buttons and chips everywhere.
- Icons inside coloured circles or rounded squares, one per list row.
- Crowns, diamonds, sparkles, rockets, fire for "premium" or "AI".
- Emoji as icons.
- Everything centred: title, subtitle, icon, button stacked in the middle.
- A phone mockup inside the app (onboarding showing a picture of the same app).
- A tab bar with two tabs.
- Shadows and glows on a dark background.
- Several accent colours, or a different colour per section or category.
- Cards inside cards. Every group in its own rounded box.
- Placeholder art: abstract gradient blobs, stock 3D illustrations, a gradient instead of real content.
- Marketing filler: "Unlock your potential", "Seamless experience", "Get Started" on every screen.

Full list with what to do instead: `references/anti-patterns.md`.

## 4. Composition rules

- **Content full-bleed.** Photos and video edge to edge, radius 0, no frame, no padding around them.
- **Lines, not cards.** Group rows with 1 pt `line` separators and a small grey section label above.
  A surface box only for a sheet or a single highlighted item (the current plan, the Pro card).
- **Selection is white, not tinted.** Selected = white fill with black text, or a 2 pt white frame.
  Unselected = `line` border or nothing.
- **Hierarchy by size and grey,** not by colour. Three text levels are enough.
- **Bottom for the thumb.** The primary button sits at the bottom, full width minus margins, 52 pt tall.
- **Same height panels.** Tool panels and sheets that switch content keep one height so nothing jumps.
- **Real content in mockups.** Real-looking photos, believable numbers and names. Never lorem ipsum
  or grey boxes. Generate images if needed, with one shared prompt skeleton so they match.
- **Honest text.** Prices, trial terms and limits are written plainly near the button.
- **Icons:** one stroke set, 1.5 to 1.6 pt, square caps, 20 to 24 pt, the colour of the text. No fills
  except play and the selected state.

## 5. Screens from recipes

Use `references/screens.md` for: onboarding, paywall, empty and permission states, grid gallery,
list and settings, editor with tool panel, bottom sheet, progress, success. Each recipe gives the
layout top to bottom with sizes. Start from the recipe and adapt it to the content.

## 6. Check before showing

Run `references/checklist.md` on every screen. Fix, then show. If something is still off, say what and why.

## Output

1. One line: the character name and its three main decisions (ground, accent, title type).
2. The tokens file for the code target.
3. Shared components (button, chip, segmented control, toggle, row, separator, badge) built on tokens.
4. The screens, in flow order.
5. With no code target, an HTML mockup per screen at 402 × 874 (iPhone) or 412 × 915 (Android),
   inline styles, real images.

For a redesign, also list what was removed (gradients, glass, extra tabs) and confirm every feature is still reachable.
